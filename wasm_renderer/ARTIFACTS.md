# WASM Artifacts — Locations & Strategy

## Artifact strategy (Phase 2)

We use **CI-built, committed baseline**:

| Artifact | Location | Role |
|----------|----------|------|
| C++ sources | `wasm_renderer/*.cpp`, `*.h` | Source of truth for renderer logic |
| JS bridge (TypeScript) | `src/wasm/bridge/*.ts`, `src/wasm/wasm_bridge.ts` | **Hand-edited SoT — edit here only. Never edit `public/wasm/bridge/*.js`.** |
| Bridge types | `src/wasm/wasm_bridge.d.ts` | Public contract for generated ESM |
| Emscripten output | `public/wasm/pixelocity_wasm.{js,wasm}` | ASYNCIFY fallback build (every browser) |
| Emscripten output | `public/wasm/pixelocity_wasm_jspi.{js,wasm}` | JSPI primary build (loaded when `WebAssembly.Suspending` exists). ~31% smaller `.wasm` — see BUILD_FLAG_EXPERIMENTS.md "Pinned build" |
| Bridge copies | `wasm_renderer/wasm_bridge.js`, `public/wasm/wasm_bridge.js`, `*/bridge/*.js` | Generated by `concat_bridge.sh` — do not edit |
| WGSL validator | `tools/naga_wasm/` → `public/wasm/naga_wasm.wasm` | GPU-less naga, built by `npm run naga-wasm:build`. Unrelated to the renderer module. |
| Validator loader | `public/wasm/naga_wasm.js` | **Hand-written**, not emitted by `emit-wasm-bridge.mjs`. Shared by Node and the browser. |
| ESM marker | `public/wasm/package.json` | `{"type":"module"}`. Everything in `public/wasm/` is already ESM; this only tells **Node** so, silencing `MODULE_TYPELESS_PACKAGE_JSON` when `verify-naga-wasm.mjs` imports the loader. Browsers ignore it. |

**Why committed binaries?** So `npm start` works on machines without Emscripten. CI always rebuilds from C++ and fails if sources change without a matching build.

**Not using Git LFS** — artifacts are ~200 KB total; CI rebuild + validation is sufficient drift protection.

## Canonical vs generated paths

```
src/wasm/bridge/*.ts + src/wasm/wasm_bridge.ts   ← EDIT HERE
        │
        ├─ webpack compiles ──► app bundle (WASMRenderer.ts)
        └─ concat_bridge.sh / esbuild
                ├─ wasm_renderer/bridge/*.js + wasm_bridge.js
                └─ public/wasm/bridge/*.js + wasm_bridge.js   (useWASM dynamic import)

wasm_renderer/main.cpp + renderer.cpp
        │
        └─ build.sh (per wasm_compile_flags.json variant)
                ├─ asyncify ──► public/wasm/pixelocity_wasm.{js,wasm}
                └─ jspi     ──► public/wasm/pixelocity_wasm_jspi.{js,wasm}

tools/naga_wasm/src/lib.rs                       ← separate crate, separate artifact
        │
        └─ cargo (wasm32) ──► public/wasm/naga_wasm.wasm
                                    ├─ node   scripts/verify-naga-wasm.mjs
                                    └─ browser src/utils/nagaWasm.ts (dynamic, out of bundle)
```

`npm run verify:wasm-bridge-sync` fails if the generated trees drift from TypeScript emit.

## Which glue did the browser load?

`src/wasm/bridge/init.ts` tries builds in `wasmArtifactOrder()`:

| Engine | Order | Loaded file |
|--------|-------|-------------|
| `WebAssembly.Suspending` **and** `WebAssembly.promising` exist (Chrome 137+) | `jspi`, then `asyncify` | `pixelocity_wasm_jspi.js`, else `pixelocity_wasm.js` |
| anything else (Safari, Firefox, older Chrome) | `asyncify` | `pixelocity_wasm.js` |

ASYNCIFY is always last in the list. If the JSPI glue fails to load or instantiate, init
drops the factory and tries ASYNCIFY. There is never a JSPI-only path.

The build that won is recorded in the diagnostics:

- `WasmBridge.getDiagnostics().wasmArtifact`: `'jspi'`, `'asyncify'`, or `null`. It is
  `null` before init, and also when a `PixelocityWASM` factory was already on `window` and
  was reused.
- `WASMRenderer.getDiagnostics().wasmArtifact`: the same value. `initSummary` reads
  `ready (jspi) · adapter: …` when init succeeds.
- Console: `[WASM] Loading <kind> build from: …`, then
  `[WASM] ✅ Initialization complete in N ms (<kind> build)`.

Both glue files register the same `PixelocityWASM` factory and use the same bridge. The five
exports that can reach `wgpuInstanceWaitAny` (`jspi.jspiExports`) always go through
`callSuspending()` (`src/wasm/bridge/call.ts`) with `{ async: true }`, on either build.

## C++ IDE index (clangd / Cursor)

`compile_commands.json` is **generated, not committed**, because its paths are
machine-absolute. The committed contract is `reports/wasm_compile_line.txt`.

```bash
npm run wasm:build              # once, so EM_CACHE holds the emdawnwebgpu port headers
npm run wasm:compile-commands   # → ./compile_commands.json (gitignored)
```

The file is rendered from `wasm_compile_flags.json` `sources`, one entry per TU. Each entry
has `--target=wasm32-unknown-emscripten`, the EM_CACHE sysroot, the compat include dir and
the emdawnwebgpu `webgpu/include` dir. No entry carries `--use-port` or `-s` flags, since a
per-TU `--use-port` is the historic `-sUSE_WEBGPU=1` leak. The repo-root `.clangd` points at
the file. Use emsdk's own `upstream/bin/clangd` so the clang version matches. CI uploads the
file as the `wasm-compile-commands` artifact. `verify:wasm-invariants` gates the committed
compile line, the per-TU flags and `.clangd`.

## Toolchain pin

| What | Value | Where |
|------|-------|-------|
| emsdk / emcc | **6.0.9** | `src/contracts/wasm_compile_flags.json` → `emsdkVersion` |
| std / opt / port / `-s` flags | one list | same JSON (`std`, `opt`, `usePort`, `sFlags`, `jsOutputName`) |
| Exports | — | `src/contracts/wasm_exports.json` |

- CI `setup-emsdk` `version:` must equal `emsdkVersion` (`npm run verify:wasm-invariants` fails otherwise). Never `latest`.
- `build.sh` runs `scripts/emcc-version-gate.sh` before `em++` and refuses a mismatched emcc. The minified glue does **not** embed the emcc version, so the gate is on the toolchain, not the artifact.
- `build.sh` and `CMakeLists.txt` both read the flag JSON; neither may hardcode `-s` flags or `--use-port` (enforced by `verify:wasm-invariants`).
- Cloud VMs / Jules: keep `SKIP_WASM_BUILD=1`. Never commit artifacts from a non-pinned emcc (e.g. 3.1.x). `ALLOW_EMCC_VERSION_MISMATCH=1` exists for local experiments only.
- Bumping the pin: change `emsdkVersion` and `ci.yml` together, rebuild, commit artifacts in the same PR.

## Build commands

```bash
npm run wasm:build      # Requires emsdk; fails if emcc missing
npm run wasm:validate   # Checks sizes, magic, exports, generated-copy equality
npm run verify:wasm-bridge-sync  # TypeScript SoT vs generated JS
npm run wasm:clean      # Remove build/ and public/wasm/
```

### Skipping WASM build intentionally
`SKIP_WASM_BUILD=1` still runs bridge concat, then skips emcc.

Headless dev VMs without Emscripten can use committed artifacts:

```bash
SKIP_WASM_BUILD=1 npm run build
```

CI jobs that consume pre-built artifacts from the `wasm` job set this automatically.

## CI pipeline

1. **`wasm` job** — installs emsdk (`mymindstorm/setup-emsdk@v14`), runs `wasm:build`, `wasm:validate`, `verify:wasm-bridge-sync`, WASM Jest smoke tests, freshness check, uploads artifacts.
2. **`test` job** — downloads WASM artifacts, runs full unit tests + CRA build with `SKIP_WASM_BUILD=1`, re-validates artifacts (`verify:toolchain-foundation` includes bridge sync).
3. **`test-wasm-e2e` job** — downloads artifacts, production build, Playwright smoke tests (`tests/wasm-renderer.smoke.spec.ts`).

See [`WASM_BUILD_CI_GUIDE.md`](../WASM_BUILD_CI_GUIDE.md) for troubleshooting.
